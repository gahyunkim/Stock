# /feat — 이슈 생성 + 브랜치 시작 워크플로우

이 스킬은 "뭔가 만들고 싶다"는 아이디어를 실제로 작업 가능한 상태(이슈 + 브랜치)로 바꿔주는 역할을 한다. 핵심은 되돌리기 번거로운 작업(이슈 생성, 브랜치 생성)은 반드시 사용자 승인 후에만 실행한다는 것이다. 그 전 단계인 "무엇을 어떻게 만들지 정리하는 것"은 자유롭게, 적극적으로 제안해도 된다.

## 전체 흐름

1. 사전 점검 (repo, git 상태, gh 인증)
2. 이슈 초안 작성 (제목/본문/라벨)
3. 구현 방식 옵션 2~3개 제안
4. 사용자에게 초안 + 옵션을 한 번에 보여주고 승인 대기
5. 승인되면 이슈 생성 → 이슈 번호로 브랜치명 결정 → 브랜치 생성 및 체크아웃
6. 결과 요약 보고

아래는 각 단계에서 실제로 무엇을 해야 하는지 설명한다.

## 0. 사전 점검

작업을 제안하기 전에 아래를 먼저 확인한다. 이걸 건너뛰면 나중에 이슈만 만들고 브랜치는 못 만드는 등 어중간한 상태가 되기 쉽다.

* `git rev-parse --show-toplevel` — git 저장소가 맞는지 확인. 실패하면 사용자에게 알리고 중단한다.
* `git status --porcelain` — 커밋 안 된 변경사항이 있는지 확인. 있다면, 곧 새 브랜치로 체크아웃할 것이므로 사용자에게 "지금 변경사항이 있는데 커밋/스태시 후 진행할지, 그대로 진행할지" 물어본다. (untracked/uncommitted 상태로 체크아웃해도 git이 알아서 따라오지만, 사용자가 인지하지 못한 채 넘어가면 혼란스러울 수 있다.)
* `gh auth status` — GitHub CLI 인증 여부 확인. 인증되어 있지 않으면 `gh auth login`을 안내하고 여기서 멈춘다. 이슈 생성은 이 스킬의 핵심 기능이므로 gh 없이는 진행할 수 없다.
* `gh repo view --json nameWithOwner,defaultBranchRef` — 어떤 저장소인지, 기본 브랜치가 무엇인지 확인해둔다.
* 저장소의 기존 컨벤션을 살짝 살펴본다: `git branch -a`로 기존 브랜치 네이밍 패턴, `gh label list`로 사용 가능한 라벨, `.github/ISSUE_TEMPLATE/` 존재 여부. 있으면 최대한 그 컨벤션을 따르고, 없으면 아래 기본값을 쓴다.

## 1. 이슈 초안 작성

사용자가 `/feat` 뒤에 적은 내용을 읽고 이슈 초안을 작성한다.

* 제목: 핵심을 담아 간결하게 (대략 50자 이내).
* 본문: 아래 구조를 기본 템플릿으로 쓰되, 저장소에 이슈 템플릿이 있으면 그걸 우선한다.
   * 배경/목표 — 왜 이 작업이 필요한지
   * 상세 설명 — 무엇을 만드는지
   * 완료 조건 (체크리스트) — 이 이슈가 끝났다고 볼 수 있는 기준
   * 참고 자료 (있다면)
* 라벨: 저장소에 관련 라벨이 있으면 제안한다 (예: `feature`, `enhancement`). 없으면 생략해도 된다 — 라벨 때문에 진행이 막히면 안 된다.

## 2. 구현 방식 옵션 제안

Stock은 Android/Kotlin 프로젝트이고 SDUI(Server-Driven UI) 경험을 위한 메인 화면 작업이 진행 중이라는 맥락을 알고 있어야 한다. 옵션을 만들 때는:

* 저장소를 실제로 훑어본다 (`build.gradle.kts`, 기존 패키지 구조, 이미 쓰이고 있는 아키텍처 패턴 — 예: MVVM, Jetpack Compose, SDUI 스키마 방식 등). 완전히 새로운 패턴을 제안하기보다, 이미 자리 잡은 패턴을 우선 존중한다.
* 현실적인 구현 방식 2~3개를 A/B/C로 제시한다. 너무 많으면 선택 피로만 생기므로 3개를 넘기지 않는다.
* 각 옵션은 다음을 포함한다:
   * 한 줄 요약
   * 장점
   * 단점/트레이드오프 (없다고 하지 말 것 — 반드시 하나는 짚는다)

## 3. 승인 대기

이슈 제목, 본문 초안, 구현 옵션(A/B/C)을 한 번에 정리해서 보여주고 사용자에게 확인받는다. 예를 들어:

```
## 이슈 초안
제목: 메인 화면 주식 관심종목 카드 SDUI로 렌더링
본문: (배경/목표 · 상세 설명 · 완료 조건 체크리스트)

## 구현 방식
A) 서버 스키마 기반 SDUI — 서버가 컴포넌트 트리 JSON을 내려주고 클라이언트는 렌더러만 담당
   장점: 서버 배포만으로 화면 변경 가능 / 단점: 초기 스키마 설계 비용 큼
B) 클라이언트 내 SDUI 시뮬레이션 — 로컬 JSON/모델로 SDUI 렌더링 구조만 우선 구현
   장점: 백엔드 없이 바로 시작 가능 / 단점: "진짜 SDUI" 경험과는 거리가 있음

어떤 방식으로 진행할까요? 이슈 내용도 수정할 부분이 있으면 알려주세요.
```

사용자가 명확히 승인하기 전까지("A로 진행해줘", "좋아, 이대로 만들어줘" 등) 절대 이슈나 브랜치를 생성하지 않는다. 수정 요청이 오면 초안을 고쳐서 다시 보여준다.

## 4. 이슈 생성

승인을 받으면 실행한다:

```bash
gh issue create --title "<제목>" --body "<본문>" [--label "<라벨>"]
```

출력되는 URL에서 이슈 번호를 파싱한다 (예: `https://github.com/owner/repo/issues/42` → `42`).

## 5. 브랜치 이름 규칙

형식: `feat-<이슈번호>-<설명-slug>`

* 설명 slug는 영문 kebab-case로 만든다 (소문자, 단어는 하이픈으로 연결, 특수문자/공백 제거). 이슈 제목이 한글이어도 브랜치명은 영어로 짧게 요약해서 만든다 — git 브랜치명 호환성과 터미널 작업 편의성 때문이다.
* 3~5단어 정도로 축약한다. 너무 길면 핵심 키워드만 남긴다.
* 예: 이슈 #42 "메인 화면 주식 관심종목 카드 SDUI로 렌더링" → `feat-42-sdui-watchlist-card`

이미 저장소에 같은 이름의 브랜치가 있으면 사용자에게 알리고 어떻게 할지 물어본다 (덮어쓸지, 이름을 조정할지).

## 6. 브랜치 생성 및 체크아웃

```bash
git checkout <default-branch>
git pull
git checkout -b feat-<이슈번호>-<설명>
```

원격에는 push하지 않는다. 이 스킬은 로컬 브랜치 생성 + 체크아웃까지만 담당한다. push는 사용자가 명시적으로 요청했을 때만 별도로 수행한다.

## 7. 마무리 보고

작업이 끝나면 다음을 정리해서 알려준다:

* 생성된 이슈 링크 (번호 포함)
* 새로 만든 브랜치 이름
* 선택된 구현 방식 요약

그리고 이제 이 브랜치에서 선택된 방식대로 실제 개발을 시작할 준비가 되었다고 안내한다.

## 주의사항

* 이슈·브랜치 생성처럼 되돌리기 번거로운 작업은 반드시 3단계(승인) 이후에만 실행한다.
* `gh` CLI가 없거나 인증되지 않았으면 즉시 알리고, "제목/본문만 초안으로 드릴 테니 직접 GitHub에서 만들어달라"는 대안을 제시한다.
* 커밋되지 않은 변경사항이 있는 상태로 새 브랜치를 만들면 그 변경사항도 새 브랜치로 함께 넘어간다는 점을 사용자가 알고 있는지 확인한다.
* Stock 프로젝트의 실제 아키텍처를 모르는 상태에서 구현 옵션을 지어내지 말고, 반드시 저장소를 먼저 훑어본 뒤 그에 맞는 옵션을 제시한다.
